## Improvement Recommendations

1. **Always run the "distractor compilation test" for integer type questions.** Any question where the blank is a type and a wider type also works is inherently P0. The generation prompt should explicitly forbid `uintN`/`intN` blanks unless overflow or explicit casting constrains the answer to exactly one type.

2. **Avoid placing blanks at mutability/visibility modifier positions.** Solidity allows multiple valid modifiers in most positions (`pure`/`view`, `public`/`external`, etc.). If the intent is to teach `pure` vs `view`, use a concept question instead.

3. **Add a validation rule: for each distractor, check if it produces compilable code.** This is the single most impactful automated check. Before accepting a code question, programmatically substitute each distractor and attempt compilation with `solc`.

4. **Improve explanation accuracy.** The gen-c5 explanation about `view` propagates a misconception. Explanations should be reviewed against Solidity docs — `view` allows but does not require state reads; `pure` forbids both reads and writes.

5. **Prefer "only-one-fits" code patterns.** The best code questions use syntax or type system constraints where exactly one option compiles (like gen-c2's `event`/`emit` pairing or gen-c1's exact byte-width requirement). Prioritize these patterns over semantic "best practice" distinctions that don't cause compilation failures.
