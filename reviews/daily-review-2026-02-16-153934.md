**1. gen-c3 — `if` distractor also compiles and works correctly**
The blank is `___BLANK___ (score >= 80)`. Substituting `if` produces:
```solidity
if (score >= 90) { return "A"; }
if (score >= 80) { return "B"; }
else { return "C"; }
```
This compiles and behaves **identically** to `else if` because every branch contains a `return` statement. The early-return pattern makes `if` and `else if` functionally equivalent here. This is a textbook early-return equivalence P0.

**Fix:** Restructure so branches assign a variable instead of returning early, making the `if` vs `else if` distinction observable:
```solidity
function getGrade(uint256 score) public pure returns (string memory grade) {
    grade = "C";
    if (score >= 90) { grade = "A"; }
    ___BLANK___ (score >= 80) { grade = "B"; }
}
```
With this structure, using bare `if` would overwrite `"A"` with `"B"` for scores >= 90, while `else if` preserves `"A"`.

## Improvement Recommendations

1. **Eliminate early-return equivalence in branching questions.** When testing `if` vs `else if`, always use assignment-based patterns rather than early returns. The generation prompt should include a rule: "If the blank tests control flow keywords, ensure branches have side effects that differ based on flow structure, not just final return values."

2. **Avoid Hardhat `console.log` questions.** `console.log` is heavily overloaded and accepts most primitive types. Questions about specific `console.logX` variants are fragile because learners (and the overloaded function) can use `console.log` for almost everything. If console logging must be tested, use a scenario where `console.log` genuinely fails or produces wrong output.

3. **Add explicit intent comments for comparison operator questions.** When testing `>=` vs `>` vs other comparisons, the code must contain an unambiguous specification of the intended behavior (e.g., a comment or a test case). Relying on real-world knowledge (voting age = 18) to disambiguate is insufficient — the code itself must make only one answer correct.

4. **Cross-check distractors against the answer for concept questions.** Before finalizing, verify that no distractor is a subset, superset, or more-precise restatement of the answer. The gen-q1 issue (block proposer is a type of validator) is a classic trap. The validation logic should flag when a distractor's meaning overlaps with the answer.

5. **Validate `console.sol` function signatures against the actual Hardhat source.** The explanation in gen-c4 claims functions "don't exist" when they do. The generation or validation pipeline should cross-reference the actual `console.sol` interface to verify which overloads exist.
